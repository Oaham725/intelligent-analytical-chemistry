# 课程共建：把教材变成一项工程

这不是把一章教材拆给学生、最后收回若干份互不相连的作业。课程共建把教材仓库作为共同工作面：每个小组在已有内容的基础上提出问题、完成修改、接受同行评审，并留下能够被后来学生继续使用和改进的版本。

## 共建目标

1. 让学生把分析化学问题转译为可检验的内容、图示与代码，而不是只复述概念。
2. 训练真实的软件协作方式：Issue 明确任务，分支承载修改，Pull Request 接受评审，合并记录形成版本历史。
3. 让教材随课程迭代。后一届学生首先理解上一届的选择与不足，再做有证据的修订。

## 课程中的三类角色

| 角色 | 主要工作 | 不应承担的工作 |
|---|---|---|
| 章节维护组 | 维护所认领章节的论证、案例、代码和知识图谱 | 擅自改变全书目录或其他章节的结论 |
| 横向评审组 | 审查另一章节的化学正确性、代码可运行性与表达清晰度 | 代替维护组重写整章 |
| 教师/助教 | 确定选题边界、维护主分支、给出最终评分与署名确认 | 为学生代写可评分的核心内容 |

每组建议 3–5 人。人数较少时可采用<a href="#/docs/course/task-map?id=12组压缩方案">12组压缩方案</a>；人数较多时按照18个章节维护组分配。

## 一个合格的章节改进应回答什么

每次修改都要回答一个具体问题，例如：

- 某个数学步骤是否让读者真正理解矩阵分解为何能够分离化学变化和噪声？
- 某段代码能否复现实验设计、光谱预处理或模型验证的关键判断？
- 某张知识图谱能否显示概念之间的因果或流程关系，而不是罗列名词？
- 新增案例是否改变了学生对“什么是可信化学信息”的理解？

“增加篇幅”“补几个概念”“把网络资料搬进来”不能单独构成任务目标。

## 学年循环

| 阶段 | 学生工作 | 平台产物 |
|---|---|---|
| 认领 | 阅读基准稿，提出待解决问题，创建 Issue | 可追踪任务卡 |
| 实施 | 在小组分支完成正文、图谱或代码改进 | 可审阅的 Pull Request |
| 评审 | 至少审阅一个其他组的 PR，提出可执行意见 | 审评记录 |
| 合并 | 根据评审修改，由教师或助教合并 | 教材新版本 |
| 归档 | 更新章节末尾的贡献者表 | 可公开的致谢记录 |

下一学年从已合并版本和遗留 Issue 开始，而不复制、覆盖或删除前一届学生的工作。

> 在公开仓库中仅署名学生自愿公开的姓名或笔名；不要在 Issue、代码注释或提交信息中写入学号、联系方式或其他个人信息。
