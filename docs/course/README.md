# 课程共建：把教材变成一项工程

这不是把一章教材拆给学生、最后收回若干份互不相连的作业。课程共建把教材仓库作为共同工作面：每个小组在已有内容的基础上提出问题、完成修改、接受同行评审，并留下能够被后来学生继续使用和改进的版本。

## 共建目标

1. 让学生把分析化学问题转译为可检验的内容、图示与代码，而不是只复述概念。
2. 把每章最基础、最容易被误解的知识画清楚：图必须解释变量、结构、过程或因果关系，不能只是概念罗列。
3. 让每一届学生为教材补入真正影响本章判断的前沿进展，并以可访问的原始论文、权威数据库或技术文档链接作为依据。
4. 把当年课程 PPT（PDF）、学生原创题和更新引文留下来，让下一届直接从已有证据、题目和图解开始改进。
5. 训练真实的软件协作方式：Issue 明确任务，分支承载修改，Pull Request 接受评审，合并记录形成版本历史。

## 课程中的三类角色

| 角色 | 主要工作 | 不应承担的工作 |
|---|---|---|
| 章节维护组 | 维护所认领章节的论证、案例、代码和知识图谱 | 擅自改变全书目录或其他章节的结论 |
| 横向评审组 | 审查另一章节的化学正确性、代码可运行性与表达清晰度 | 代替维护组重写整章 |
| 教师/助教 | 确定选题边界、维护主分支、给出最终评分与署名确认 | 为学生代写可评分的核心内容 |

每组建议 3–5 人。人数较少时可采用<a href="#/docs/course/task-map?id=12组压缩方案">12组压缩方案</a>；人数较多时按照18个章节维护组分配。

## 一个合格的章节改进应回答什么

每次修改都要回答一个具体问题，例如：

- 某个数学步骤是否让读者真正理解矩阵分解为何能够分离化学变化和噪声？
- 某段代码能否复现实验设计、光谱预处理或模型验证的关键判断？
- 某张知识图谱能否显示概念之间的因果或流程关系，而不是罗列名词？
- 新增的前沿论文、仪器进展或开源模型是否真正改变了学生对本章问题边界、方法选择或失效条件的理解？

“增加篇幅”“补几个概念”“把网络资料搬进来”不能单独构成任务目标。每个年度维护组至少应形成以下三类可验收成果：

| 必交成果 | 要求 | 留存位置 |
|---|---|---|
| 基础知识图解 | 新增或实质修订 1 幅可编辑 SVG；图中变量、箭头、符号和边界条件须在正文解释 | `assets/graphs/chXX.svg` 及章节正文 |
| 前沿更新卡 | 围绕一个近年进展，说明“新在哪里、能解决什么、仍受什么限制”，并附原始来源链接 | 章节正文与年度引文页 |
| 传承题 | 新增或修订 1 道面向下一届的题目，附答案要点、考查目标和来源/数据说明 | 年度题库页或相应代码目录 |

## 学年循环

| 阶段 | 学生工作 | 平台产物 |
|---|---|---|
| 认领 | 阅读基准稿，提出待解决问题，创建 Issue | 可追踪任务卡 |
| 实施 | 在小组分支完成正文、基础知识图解、前沿更新卡、传承题或代码改进 | 可审阅的 Pull Request |
| 评审 | 至少审阅一个其他组的 PR，提出可执行意见 | 审评记录 |
| 合并 | 根据评审修改，由教师或助教合并 | 教材新版本 |
| 归档 | 更新章节末尾的贡献者表 | 可公开的致谢记录 |

下一学年从已合并版本和遗留 Issue 开始，而不复制、覆盖或删除前一届学生的工作。

## 年度资料的归档位置

每个学年使用 `resources/annual/学年/` 保存课程资料：`ppt/` 用于教师提供的课件 PDF，`questions/` 用于留给下一届的学生题，`references/` 用于本年度新增或更正的引文。当前入口见<a href="#/resources/annual/README">年度资料、传承题与引文</a>；每章末尾也提供直达链接。

> 在公开仓库中仅署名学生自愿公开的姓名或笔名；不要在 Issue、代码注释或提交信息中写入学号、联系方式或其他个人信息。
