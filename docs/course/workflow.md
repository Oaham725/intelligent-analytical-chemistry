# 提交与评审流程

## 1. 先创建任务卡，再开始修改

每项工作先在 GitHub 创建 Issue，写清楚：对应章节、要解决的问题、预计修改的文件、可检查的完成标准。一个 Issue 只解决一个相对独立的问题。

示例：

> **问题**：第3章用文字说明 PCA，但未显示 SVD 与低秩近似的关系。
>
> **修改**：补充矩阵分解图示，增加 `code/ch03_exercises/01_pca_svd.py` 的误差比较输出。
>
> **验收**：随机矩阵和光谱矩阵都可运行；图示与正文符号一致；至少一名非本组同学复现。

## 2. 在独立分支上工作

分支命名采用：

```text
ch03/pca-svd-explanation
ch09/raman-baseline-exercise
docs/course-rubric-clarification
```

不要直接向 `main` 分支提交。每次提交只包含同一项任务相关的文字、代码、图或链接；不要在一个提交中格式化整个仓库，也不要覆盖其他组的文件。

## 3. Pull Request 是作业的正式交付物

提交 PR 时，必须关联 Issue，并说明：

- 本次修改解决的分析化学问题；
- 修改了哪些正文、代码、SVG或数据文件；
- 如何运行代码或核查图表；
- 仍然存在的限制或未解决问题；
- 建议由哪一组交叉评审。

代码改动应在 PR 描述中给出最短运行命令和预期现象。仅上传截图、Word 文件或不可运行片段，不构成代码交付。

## 4. 交叉评审

每个维护组至少完成一次对其他章节的实质性评审。评审意见应当可操作，例如指出公式符号不一致、训练/测试划分泄露、图谱缺少因果关系、代码无法复现或结论超过数据支持范围。

“很好”“建议更详细”等不构成有效评审。维护组应逐条回复，必要时更新 PR。

## 5. 合并与归档

教师或助教确认以下条件后合并：

1. Issue 目标已完成，且 PR 描述能说明验证方式；
2. 至少有一次有效交叉评审；
3. 代码、链接和 SVG 均能打开或运行；
4. 章节末尾的“本章共建记录与致谢”已按模板更新。

合并后的提交即为本学年的教材版本。发现问题时新建 Issue 修订，不回退、覆盖或抹去既有贡献。
